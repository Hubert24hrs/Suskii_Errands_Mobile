# supabase/ — database, auth hooks, Edge Functions

Owner: Claude Code. Design sources: [ERD](../docs/plan/erd.md), [RLS policy matrix](../docs/plan/rls-policy-matrix.md), [infra and CI/CD plan](../docs/plan/infra-cicd.md), [ADR-0013](../docs/adr/0013-backend-foundation-before-contracts-v1.md).

## Layout

| Path | What |
|---|---|
| `config.toml` | Local stack and project settings: exposed schemas (`public` only), phone and email auth, TOTP MFA, auth hooks |
| `migrations/` | Timestamped SQL, applied in order by the Supabase CLI. Pre-contract migrations are editable until a shared environment applies them (ADR-0013) |
| `seed/` | **Dev and staging only.** Countries, cities, legal document placeholders, flags, remote config |
| `tests/database/` | pgTAP suites. `00_structure_test.sql` guards grants, RLS, `search_path` and money column types for every future migration |
| `local-fallback/` | Runner for machines without Docker: a Supabase shim plus a script for plain PostgreSQL 17 + PostGIS. Kept outside `tests/` because `supabase test db` runs every `.sql` file under it |
| `functions/` | Edge Functions (Deno 2 workspace). `_shared/` holds dependency-free modules; each function keeps a testable `handler.ts` and a thin `index.ts` that wires `@supabase/server` and environment |
| `.env.example` | Local secrets template (copy to git-ignored `supabase/.env`) |

Every function is wrapped by `_shared/observability.ts`: an `x-request-id` response header, one structured `request.completed` log line (status, duration, region), and uncaught errors reported to Sentry when `SENTRY_DSN` is set — with request, user, breadcrumbs and extras stripped in `beforeSend` so tokens, OTPs and phone numbers never leave the function.

Environment: `SENTRY_DSN`, `SUSKII_RELEASE`, `SEND_SMS_HOOK_SECRETS`, `SUSKII_ENV`, `ANDROID_SMS_RETRIEVER_HASH`, `ANDROID_PACKAGE_NAME`, `GOOGLE_PLAY_INTEGRITY_SERVICE_ACCOUNT`, `IOS_APP_ID`, `APP_ATTEST_ENVIRONMENT`, `APP_ATTEST_VALIDATION_CATEGORIES` (see `.env.example`). `SUPABASE_URL` and the API keys are provided by the platform.

Marketplace (Phase 3, in progress): `service_categories` and `requests` with `create_request` → `publish_request` → `cancel_request`, all idempotent. A customer edits only a draft, and only the fields a draft carries; `status` is never client-writable; providers never select `requests` (their feed will come from matching). `private.expire_requests()` closes requests nobody took, every five minutes.

Negotiation (Phase 3): `offer_threads`, `offers` and `pricing_guardrails`, with `create_offer`, `counter_offer`, `accept_offer`, `decline_offer` and `withdraw_offer`. One thread per provider per request; offers are append-only, so a change is a new row and the whole history stays visible. The same side may not answer itself, and the counterparty is the one who accepts. `accept_offer` is the S-10 transaction: lock the request row, accept, expire every sibling offer, close the threads, emit exactly one event. A provider reads only their own thread — a rival's amount is not filtered out by the client, it is never selectable. `private.expire_offers()` runs every minute and puts a request with no live offer back into the feed; a request that is cancelled or expires takes its live offers with it by trigger.

Providers and matching (Phase 3): `provider_profiles`, `provider_services`, `provider_service_areas` and the hot `provider_live_location`, with `set_online`, `update_provider_services`, `update_provider_service_areas`, `heartbeat`, `provider_feed` and `private.match_providers`. `heartbeat` is movement-gated (25 m or 60 s, both remote config) because S-06 measured write rate, not query shape, as the limit; the location table carries that spike's storage settings. `provider_feed` is the **only** way a provider sees open work — one radius, their own country, their registered categories, and a **distance rather than the customer's coordinates**. `match_providers` scores candidates for the notification fan-out with weights from `remote_config`, no model (ai-design §9). Nobody selects `provider_live_location`: RLS is forced and there is no policy for `authenticated` at all.

Jobs (Phase 3): `jobs`, `job_events` (append-only, monthly partitions) and `private.job_pins`, with `set_job_status`, `verify_pin`, `reveal_job_pin`, `confirm_completion` and the scheduled `private.auto_confirm_jobs()`. A job row appears by trigger when an offer is accepted; its money columns stay NULL until the payment phase writes the snapshot once. `private.mark_paid_held()` is the payment seam and has no client grant. PINs are salted, hashed and attempt-limited; a wrong PIN returns `{verified: false, attempts_remaining}` rather than raising, because raising would roll back the very counter that limits it.

Proofs and marketplace media (Phase 3): buckets `request-media` (`<user_id>/<file>`, the customer's own folder, readable by the provider actually doing the job) and `job-proofs` (`<request_id>/<file>`, readable by that job's participants, writable by its provider, with no delete policy — a proof that can be removed is not one). `public.proofs` records each item with the **server's** timestamp as the authoritative one and the device's time and point beside it as dispute context. `submit_proof` is the only way in. Proof completeness is the category's `proof_requirements` (`{"photo": 1, "receipt": 1}`), enforced by a trigger on the transition into `completed_by_provider` so it holds on every path. **EXIF is not stripped yet**: the re-encode worker does not exist, so clients must strip metadata before upload; `proofs.display_path` is where that rendition will land.

Ratings and reputation (Phase 3): `public.ratings` with `rate_job`, the scheduled `private.close_rating_windows()` and `private.recompute_reputation_all()`. SH-30's blind period is a column: a rating carries `visible_at`, NULL until both sides have rated or the window closes, and the RLS policy hides everything but your own until then. Aggregates on `provider_profiles` are written by the job, never by a trigger, and use Bayesian smoothing (prior 4.5 stars with the weight of ten jobs, both remote config) so one rating cannot make or break a provider. Only **visible** ratings count, since an average that moved during the blind period would leak the rating it came from. `profiles.trust_level` is deliberately not computed: SH-31 ties TRUSTED and above to address verification, which is Phase 4.

Chat and channels (Phase 3): `conversations`, `messages` (monthly partitions, append-through-`send_message`), `message_reads`, the `chat-media` bucket, and `private.may_join_topic` behind the policies on `realtime.messages`. Chat opens at assignment and closes a day after confirmation (`chat_window_hours_after_confirm`), staying open while a dispute is live; nobody outside a job can message anybody, which is deliberate — a losing bidder has no route to the customer. Moderation fails open per OD-21: messages deliver as `pending`, and `rejected` is what hides one, though never from its own author. Realtime authorisation is **[A]** until S-02 runs against a real project; `17_chat_test.sql` asserts the policies are bound and tests the topic rules directly, but the binding between a joined channel and those policies is Supabase's, unverified by us.

Relationships and business (Phase 3): `blocks`, `favorites`, `reports`; `organizations`, `organization_members`, `vehicles`, `zones`. A blocked pair is never matched again — filtered in matching and the feed, refused by trigger in offers and chat. Nobody is told they were blocked or reported. Organisations need consent to join and lose access the moment a member is removed; role guards are null-safe, because `org_role()` returns NULL for a non-member and a bare `<>` against NULL admits everybody (audit C.1). Zone rules ban a vehicle where a city bans it; the polygons are the client's to draw and the table ships empty, so an empty map bans nobody.

Notifications and fan-out (Phase 3): `notifications` (monthly partitions), `private.fan_out_request` on publish plus a two-minute sweep, and `private.broadcast` on the private channels. Notifications are keys and params, never sentences; the chat one carries no body, and the losing provider's carries nothing about who won. Broadcasts are a courtesy — a channel that is down is noticed, not propagated, because the tables are the truth.

Safety (Phase 4): `trusted_contacts`, `sos_partners`, `sos_incidents` and `trip_share_links`, with `add_trusted_contact`, `remove_trusted_contact`, `raise_sos`, `update_sos_incident`, `create_trip_share`, `revoke_trip_share`, `get_shared_trip` and the scheduled `private.escalate_unacked_sos()`. Raising SOS writes the incident, tells operations, records the partner dispatch and counts the trusted contacts in one transaction; pressing again joins the open incident rather than opening a second case. Trusted contacts are capped at five by trigger and their numbers arrive encrypted (ADR-0007) — nothing in SQL decrypts them. A share link is a token whose **hash** is stored: it is returned once, expires, can be revoked, and stops working the moment the job ends. `get_shared_trip(token)` is the **only** function `anon` may call besides `get_bootstrap`, and it returns the least that is useful — job status and the provider's position, no names, no addresses, no amounts. `sos_partners` ships empty because no partner is contracted (client action 12); `secret_ref` names a Vault entry and never holds a secret.

Verification (Phase 4): the KYC spine lives in the `kyc` schema, which **no client role can reach** — `kyc.verification_sessions`, `kyc.kyc_steps`, `kyc.identity_documents`, `kyc.police_clearances` and the append-only `audit.kyc_access`. Everything a person or an officer does goes through `start_verification_session`, `submit_kyc_step`, `submit_identity_document`, `submit_police_clearance`, `get_my_kyc_profile`, `kyc_review_queue`, `decide_kyc_step`, `request_document_access` and `verification_summary`; `private.record_vendor_check` is the seam the identity vendor's answer arrives through (Smile ID is unsigned — OD-13 — so nothing calls it yet). Document numbers arrive as ciphertext plus a keyed blind index (ADR-0007); the blind index is UNIQUE, so one identity backs one account and nothing in SQL reads either value. A rejection carries a reason key, never prose. An officer never reviews their own step, support sees status and never a document, and asking for a document is logged before any URL exists. `private.expire_kyc_documents()` lapses a certificate that has run out and the standing with it, which is what stops a provider taking new work.

Moderation (Phase 4): `prohibited_items` — the rule table — and `moderation_cases`, with `private.moderate_text`, the `requests_moderate`, `messages_moderate` and `ratings_moderate` triggers, and `moderation_queue` / `decide_moderation_case` for the reviewer. **The deterministic rules run first and a model cannot overrule them** (ai-design §8): terms are matched on word boundaries, and the column's CHECK admits no regular-expression metacharacter, so a rule an operator edits cannot become a rule that matches everything. **Moderation never bans anyone** — upholding a case takes the content down and leaves the account alone. Everything fails open per OD-21: a held request publishes, a flagged message delivers, and only a `block`-severity match is refused outright, with `ERR_CONTENT_NOT_ALLOWED` naming the rule that fired so a screen can say which. The global baseline ships in the migration rather than the seed, because a production database that moderates nothing is the failure the table exists to prevent; the five researched countries' own rules ship with the dev seed, since a country row does not exist until its pack is approved. Every rule is **[A]**: each pack tags `restricted: assumption`, awaiting counsel.

Risk (Phase 4): `fraud_flags`, `private.raise_fraud_flag` and the rules — three immediate signals (a mocked position on a heartbeat, a failed device-integrity verdict, and a job whose customer and provider share a device fingerprint) and an hourly sweep (`private.run_risk_rules()`: device reuse, collusive pairs, request and offer velocity, cancellation abuse). Thresholds are `remote_config` keys prefixed `risk_`. **Nothing here bans, suspends, holds money or refuses a job** — a rule raises a flag and `review_fraud_flag` records a person's decision; the enforcement that may follow is separate, explicit and audited (OD-25). A partial unique index keeps one open flag per subject per rule, which is what makes an hourly sweep safe. The subject of a flag cannot read it: `fraud_flags` is visible to reviewers only, because a score you can see is a score you can tune against. Chargeback rules are named in the spec and are not built — there is no gateway until Phase 5, and a rule that silently never fires is worse than an absent one.

Communication (Phase 6): `calls` and `masked_numbers`, with `start_call`, `answer_call`, `end_call` and `request_pstn_fallback`, plus the one-minute `private.expire_calls()`. **There is no recording column and none may be added** — the spec says metadata only and the DPIA was written on that basis, so `25_calls_test.sql` asserts structurally that no column of `calls` mentions recording or transcripts. The server reads the callee off the job rather than taking one from the caller; the call window is `private.chat_is_open`, the same rule as chat rather than a second copy of it; and two people ringing each other at once get one call, with `is_caller` telling the second they are now the callee. A caller hanging up on a ring is a missed call, the callee doing it is a decline — derived server-side, because a client that labelled its own calls could rewrite the other party's history. A missed call writes a system message into the job chat and a push (SH-15). The LiveKit access token is **not** minted here: `start_call` returns the room name and the identity it must carry, and signing it needs an API key that belongs in an Edge Function's environment, for an account nobody has opened yet (REPORT §6.1). PSTN masking is a seam for the same reason — no telephony provider is contracted (REPORT §6.3), so `request_pstn_fallback` returns NULL and emits `call.pstn_requested`, which at least makes the demand measurable before anybody buys numbers. It returns rather than raises deliberately: an exception would roll that event back with the rest of the transaction, and the count is the only thing the seam is currently good for. `private.record_masked_number` is where the worker writes an allocation back.

Notification delivery (Phase 6): `private.notification_channels` decides which of push, SMS, email and WhatsApp a notification actually goes out on, from `notification_preferences` and quiet hours, and `private.notify` carries the answer on the outbox event so no sender re-derives it and two senders cannot disagree. Job-critical kinds are never suppressed (SH-16); SOS and payment failure belong in that set and are named in the function as not yet being in it, because SOS reaches operations through the outbox and payment does not exist until Phase 5. Quiet hours need a clock, so `profiles.timezone` is new and client-writable — `country_code` does not answer it, since a Nigerian in London should not be woken at 3 a.m. Lagos time; an unknown zone name falls back through the country's first city to UTC rather than raising inside a trigger. The inbox row is written whatever the channels say: it is the record, not a channel. The push payload rule (DF rule 1, SH-17 — an id and a generic title, nothing else) is the sender's obligation, and `notification_id` is on the event so it can meet it.

Scheduled errands (Phase 6): a request with `scheduled_at` stays a draft — editable and cancellable, which is what CU-32 promises — and `private.publish_scheduled_requests()` publishes it `scheduled_publish_lead_minutes` before the hour. Both it and `publish_request` go through `private.do_publish_request`, so a guard added to one is a guard in both. Each request publishes in its own subtransaction: one that cannot go out must not take the batch with it, and its customer is told with a reason key rather than a raw database message.

Support and admin (Phase 8): `support_tickets` and `ticket_messages`, with `open_ticket`, `reply_to_ticket`, `ticket_queue` and `update_ticket`. A ticket message can be **internal** — a note to a colleague rather than a reply — because without that, everything a support agent writes while working out what happened is addressed to the customer, so it gets written somewhere unauditable or not written at all. The real point of the table is `private.support_ticket_scope`: it closes audit finding S.1, where the Phase 3 policies let every support agent read **every** conversation, message and call, while the RLS matrix said support reads a job's chat only when a ticket names it. Support is now scoped to ticketed jobs, and `dispute_officer` loses the access rather than keeping an unscoped one until `disputes` is built in Phase 5. `open_ticket` refuses a `request_id` the caller is not on, because the request id is exactly what widens a support agent's reach.

Suspension (Phase 8): `suspend_provider` and `reinstate_provider`, super admin only, audited, with a reason key the provider is actually told. This is the explicit decision OD-25 keeps out of the risk engine, and it is **bounded** — an end date is required and capped at a year, so a permanent ban with no appeal is not something one function call can do. Reinstatement is what makes suspension safe to use at all.

Money (Phase 5): the double-entry ledger in `ledger` — `accounts`, `transactions`, `entries`, `balances` — with the thirteen-account chart from ADR-0011. The spec names nine; double entry needs four more, because without an asset account there is nothing to debit when a customer pays, and splitting that asset into `gateway_pending` and `gateway_available` is what makes daily reconciliation mechanical. `ledger.post` is the only way money is written down: signed minor units, one currency per transaction, no zero entries, at least two entries, and the whole set summing to zero. **It validates before it writes.** S-14 found that a `DEFERRABLE INITIALLY DEFERRED` constraint trigger fires outside any PL/pgSQL exception handler, so the posting function cannot catch it and the abort takes every other row in the transaction with it — audit entries, outbox records, everything. So the check runs first and raises a catchable `P0001`, and the deferred trigger stays as the invariant no future code path can route around. Balances are a materialised convenience; `entries` is the truth, and `ledger.reconcile()` compares them nightly through `private.record_health_check` rather than raising at 03:00 where nobody would see it. Accounts are created on first use, because a chart seeded ahead of time is thirteen rows per currency per user, nearly all of them zero for ever. `public.my_balances()` is the only client-facing read, and it negates: these are liabilities in the books, so a credit balance is money owed *to* the user, and showing them a negative number would be true bookkeeping and a terrible answer.

Payments (Phase 5): `payments`, partitioned `webhook_events`, and the four seams a gateway worker writes back through. `start_payment` is transition 7 — it creates an intent, takes the money snapshot (rate, commission, net, written once so a country changing its commission next month cannot reach a job already agreed), and emits `payment.requested`; `checkout_url` stays NULL because nothing exists to create a checkout. **A client never confirms a payment.** `private.confirm_payment` has no grant to any client role — `29_payments_test.sql` asserts that directly — and the only path into `paid_held` is a signature-verified webhook plus a server-side verify, which is transition 8 and posting 1a. `private.ingest_webhook` stores the raw payload before anything acts on it and de-duplicates on the gateway's own event id, by an explicit check rather than by the unique index: a partitioned table's unique index must carry the partition key, so the index alone would miss a retry that crossed a month boundary. An invalid signature is stored and marked rather than discarded, because it is evidence somebody tried. Earnings are recognised by an hourly sweep after `settlement_hold_hours`, not at confirmation — money released before the dispute window closes is money to be clawed back from somebody who has already spent it. A payment nobody completed returns the job to `agreed` with a `payment_ttl_expired` event, so the customer keeps the price they negotiated.

Cancellations and refunds (Phase 5): `cancel_job` is the paid half — `cancel_request` still covers a request nobody has paid for. What a cancellation costs is `private.cancellation_fee_minor`, one function rather than a number scattered about: nothing before the provider is `en_route`, `cancellation_fee_bps` after it (10% by default, OD-19's proposal), and nothing at all when the provider is the one cancelling — a provider who abandons a job should not be able to charge for it, and their cancellation rate is the consequence the risk engine already watches. OD-08 decides the gateway fee: the platform absorbs it except on a late customer cancellation, where it comes out of the refund. Both are `remote_config`, because both are the client's to change. A refund is `pending` until the gateway confirms it, but the money leaves `held_funds` for `refunds_payable` immediately — the platform owes it from the moment it cancels. `private.fail_refund` posts **nothing** to the ledger for the same reason: the money has not moved, so the books must not say it has. The sum of refunds against a payment is bounded by a deferred constraint trigger, which is a backstop and not a guard — the partial refunds disputes will bring must check first and raise catchably (S-14).

Promos and tips (Phase 5): `promo_codes`, `promo_redemptions` and `tips`, with `preview_promo` so the number a customer is shown and the discount they get are the same arithmetic. **A promo never reduces provider earnings** — commission is taken on the full negotiated price and the discount is booked as `platform_promo_expense` (posting 4b, and the spec). **A tip carries no commission**, though the gateway's fee on the tip charge still comes out of it: the platform neither profits from a tip nor subsidises one (posting 2). Budgets move under a row lock in the same transaction as the redemption, because a budget two people can exceed at once is not a budget. `promo_codes` is granted column by column: `spent_minor` and `max_uses` are not among them, since a customer who could read the budget would know exactly when to hurry. A tip is a `payments` row with `kind = 'tip'`, so it takes the same webhook path as a job payment and can sit alongside one; `start_payment` was dropped and recreated with its promo argument rather than overloaded, because two overloads with defaults would make the short call ambiguous instead of defaulting.

The item float (Phase 5): a shopping errand carries two amounts — what the provider is paid for going, and what the goods cost — and **they are not the same kind of money**. The float is the customer's money passing through the provider's hands to a shopkeeper, so it carries no commission, it is reimbursed against a receipt, and the remainder goes back. Treating it as part of the job price would take 12.5% of somebody's groceries. The customer also pays the gateway's fee on the float as a surcharge (OD-04), because otherwise the provider would be reimbursed less than they spent, which is not a reimbursement — that surcharge rate is the **only estimate in the money path**, and it is `remote_config` for exactly that reason. `payments` now records `job_amount_minor`, `float_minor` and `float_surcharge_minor`, so nothing re-derives the split; `start_payment`, `confirm_payment`, `recognise_earnings` and `cancel_job` were all replaced to read them. Earnings will not settle while a float is unapproved — settling around it would strand the goods money in a holding account nobody watches — and `cancel_job` refuses once a float has been released, because unwinding money already spent in a shop is a dispute.

Disputes (Phase 5): `disputes` and `dispute_evidence`, with `open_dispute`, `submit_dispute_evidence`, `withdraw_dispute` and the officer's `dispute_queue`, `assign_dispute` and `resolve_dispute`. Three places already said "that is a dispute, not a cancellation" — moderation, `cancel_job` and the item float — and pointed at a table that did not exist; so did `dispute_officer`, which lost its blanket read of chat when support was scoped to tickets and had **no scoped access at all** until `private.dispute_scope` gave it one. Opening a dispute **freezes the money rather than moving it**: the job goes to `disputed`, which is a status the settlement sweep does not pick up. `frozen_from` records what it froze, because withdrawing has to restore that exactly — assuming `confirmed` would mark unfinished work finished and release its money. Each side reads only its own evidence: evidence you can read before you answer it is evidence you can tailor a story around. Nobody adjudicates a job they were on, checked for the assignee in `assign_dispute` and for the caller in `resolve_dispute`. **The refund total is checked in the function and raised catchably** — the invariant on `refunds` is a deferred constraint trigger whose abort cannot be caught, `cancel_job` could not breach it by construction, and a partial refund decided by a person is the first thing that can (S-14).

No gateway is integrated and none can be: Flutterwave and Paystack need merchant accounts the client has not opened (timeline action 4). That does not block the ledger, which is why it exists first — `28_ledger_test.sql` posts the spec's own worked example through money-flows 1a–1d and checks the platform ends with 12.50 in cash, 12.50 of revenue, 2.19 still owed to a referrer and net revenue of exactly 10.31.

Storage: `avatars` and `kyc-docs`, both private, created by migration `…120200_storage_buckets`. Every object lives at `<bucket>/<user_id>/<file>`; policies allow a user their own folder only. `kyc-docs` is **write-only for clients** — identity documents go in and never come back out to a browser or app, so a stolen session cannot re-read them; review and backups read with the service role. `tests/e2e/storage_e2e.sh` proves all of it against the real Storage API in CI.

Sessions (SH-38): `list_sessions()`, `revoke_session(id)` and `revoke_other_sessions()` read and delete `auth.sessions` for the caller. Deleting a session cascades to its refresh tokens, so it cannot be refreshed; an access token already issued stays valid until `jwt_expiry` (1 hour). `tests/e2e/sessions_e2e.sh` proves both against a real GoTrue in CI.

Error convention for client-callable functions: `28000 ERR_UNAUTHENTICATED`, `42501 ERR_*` not allowed, `P0001 ERR_*` business rule, `22023 ERR_*` invalid argument. The message is the stable code the apps localise.

## Deploying

Google and Apple sign-in are switched on per environment by `GOOGLE_CLIENT_IDS` / `APPLE_CLIENT_IDS` (native `signInWithIdToken` needs only client IDs); the writer refuses values that could break the generated TOML and is tested by `deploy/write-remote-config_test.sh` in `backend-db.yaml`. Deploys never run from a laptop. `pipeline-main.yaml` runs the checks on every push to `main`, then deploys dev and staging when `DEPLOY_DEV_ENABLED` / `DEPLOY_STAGING_ENABLED` are `true`; production is promoted by hand with `deploy-production.yaml`; `rollback-functions.yaml` redeploys an earlier commit's functions. Each deploy: migrations (dry run, apply) → function secrets from GCP Secret Manager → functions → `config push` with a `[remotes.deploy]` block generated by `deploy/write-remote-config.sh` → health smoke test on the new release. Procedures and the setup checklist: [RB-14](../docs/runbooks/RB-14-backend-deploy-and-rollback.md).

## Rules for new migrations

- Every table in `public`: `ENABLE` and `FORCE ROW LEVEL SECURITY`, `REVOKE ALL … FROM anon, authenticated`, then the exact grants from the RLS matrix. Client-writable columns are column grants.
- Policies wrap `auth.uid()` and helper calls in `(SELECT …)` and keep one permissive policy per role and action (advisors fail CI on warnings).
- Every function: `SET search_path = ''`, `REVOKE ALL … FROM PUBLIC`, explicit `GRANT EXECUTE`. Client-callable ones go on the allowlist in `00_structure_test.sql`.
- Money columns are `*_minor bigint` with a currency code; rates are `*_bps integer`; rounding goes through `private.apply_bps`.
- Creates, transitions and money operations take an idempotency key via `private.idempotency_claim` / `private.idempotency_complete`.
- A migration ships with its pgTAP allow **and** deny tests in the same change.
