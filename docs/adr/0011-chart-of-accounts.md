# ADR-0011 — Extend the spec's ledger accounts with gateway assets and two expense accounts

| | |
|---|---|
| Status | Accepted |
| Date | 2026-09-16 |
| Deciders | Claude Code |
| Unblocked by | — |

## Context

The spec defines a double-entry, append-only ledger with nine accounts: `customer_wallet`, `provider_earnings`, `referral_earnings`, `platform_revenue`, `platform_promo_expense`, `gateway_fees`, `held_funds`, `item_float`, `refunds_payable`.

Writing out every money path in [money-flows.md](../plan/money-flows.md) — generated by a script that asserts each transaction is zero-sum — showed that this list cannot balance on its own:

1. **There is no asset account.** When a customer pays, `held_funds` is credited (a liability rises), but nothing can be debited. Every one of the nine accounts is a liability, revenue or expense. A double-entry ledger needs somewhere for the cash to be.
2. **Referral cost is not separable.** The spec defines `platform_revenue = platform_commission − referral_commissions − promos`. Promos have their own expense account; referrals do not, so the referral cost would have to be netted directly against revenue, which loses the gross commission figure finance reports need.
3. **Chargebacks have nowhere to land.** A chargeback fee is neither a gateway collection fee nor revenue.

## Decision

We will keep all nine spec accounts with their spec meaning, and add four:

| Account | Type | Purpose |
|---|---|---|
| `gateway_pending` | Asset | Captured by the gateway, not yet settled to the merchant balance |
| `gateway_available` | Asset | Settled into the merchant balance and spendable |
| `platform_referral_expense` | Expense | Referral commission funded by the platform (OD-01 default) |
| `chargeback_losses` | Expense | Chargeback fees and amounts that cannot be recovered |

Both gateway asset accounts are held **per gateway and per currency**, like every other account.

Signs follow spike S-14: debit positive, credit negative, integer minor units. Balances are derived from entries; the materialised balance table carries a version for optimistic locking, as the spec requires.

## Consequences

**Good:** every flow in the spec balances, including item floats, promos, partial refunds, chargebacks and payout reversals. Splitting pending from available makes daily reconciliation a direct comparison — pending against the gateway's receivable, available against the merchant balance — instead of an inference. Gross commission and referral cost are separately reportable.

**Bad / costs:** four more accounts to seed per gateway and currency, and the reconciliation job must post the pending-to-available transfer when each settlement report arrives, or `gateway_pending` grows without bound. That growth is itself a useful alert.

**Follow-on work:** account seeding in Phase 5 migrations; reconciliation job and runbook RB-03; finance reports built on `platform_revenue − platform_referral_expense − platform_promo_expense`.

## Alternatives considered

| Option | Why not |
|---|---|
| Single `gateway_balance` asset | Balances, but reconciliation can no longer tell "not settled yet" from "missing" |
| Net referral cost directly against `platform_revenue` | Loses gross commission; finance cannot report commission and referral cost separately |
| Single-entry balances per user | Rejected by the spec, which requires double entry |

## Revisit when

A gateway exposes sub-balances we need to mirror (for example a reserve held back from settlement), or a country's accounting rules require a different treatment of held customer funds (OD-12).
