This document shows, for every money path the spec names, what the gateway does and exactly which ledger entries are posted. It is the reference the Phase 5 posting functions are tested against.

## Conventions

- **Signed minor units:** debit positive, credit negative (S-14). Amounts shown in USD for readability; storage is always integer minor units with a currency code.
- **One currency per transaction.** A job is priced and settled in its country's currency (spec).
- **Every transaction sums to zero.** Enforced by a deferred constraint trigger, and validated in the posting function first because a deferred violation cannot be caught (S-14).
- **Rounding** is `round_half_even` at minor units, applied when an amount is computed, never on storage.
- **Worked example:** the spec's USD 100.00 job — 12.50 commission, 87.50 net, 2.19 referral — plus a gateway collection fee of 2.90 and a payout transfer fee of 0.50. Fees are illustrative; real ones are read from the gateway response (ADR-0003).

## Chart of accounts

The spec lists nine accounts. Double entry needs four more, recorded in [ADR-0011](../adr/0011-chart-of-accounts.md):

| Account | Type | Normal balance | Source |
|---|---|---|---|
| `gateway_pending` | Asset | debit | **Added** — captured but not yet settled by the gateway |
| `gateway_available` | Asset | debit | **Added** — settled into the merchant balance, spendable |
| `held_funds` | Liability | credit | Spec |
| `item_float` | Liability | credit | Spec |
| `refunds_payable` | Liability | credit | Spec |
| `customer_wallet` | Liability | credit | Spec |
| `provider_earnings` | Liability | credit | Spec |
| `referral_earnings` | Liability | credit | Spec |
| `platform_revenue` | Revenue | credit | Spec |
| `gateway_fees` | Expense | debit | Spec |
| `platform_promo_expense` | Expense | debit | Spec |
| `platform_referral_expense` | Expense | debit | **Added** — makes the spec's `platform_revenue − referral_commissions` reportable |
| `chargeback_losses` | Expense | debit | **Added** — chargeback fees and unrecovered amounts |

Without an asset account there is nothing to debit when a customer pays, so the ledger cannot balance. Splitting it into pending and available is what makes the spec's daily reconciliation mechanical: pending must match what the gateway says it owes us, available must match the merchant balance.

## The standard job, end to end

```mermaid
sequenceDiagram
    autonumber
    participant C as Customer app
    participant API as accept_offer / start_payment
    participant GW as Gateway (Flutterwave / Paystack)
    participant WH as Webhook function
    participant L as Ledger
    participant W as Settlement worker
    participant P as Provider

    C->>API: accept_offer(idempotency_key)
    API->>API: lock request, snapshot commission_rate_bps + agreed amount
    C->>API: start_payment(method, idempotency_key)
    API->>GW: create hosted checkout (server-initialised, merchant bears fee)
    API-->>C: checkout URL (Custom Tab / SFSafariViewController)
    C->>GW: pays
    GW->>WH: charge.completed webhook
    WH->>WH: verify signature, store raw, de-duplicate on event id
    WH->>GW: verify transaction (server-side)
    WH->>L: post 1a — held_funds credited
    WH->>API: PAYMENT_PENDING → PAID_HELD
    Note over GW,L: T+1..T+5: settlement report → post 1b
    Note over C,P: job runs; customer confirms; dispute window elapses
    W->>L: post 1c — earnings recognised
    W->>GW: create transfer to verified payout account
    GW->>WH: transfer.completed webhook
    WH->>L: post 1d — provider paid
    WH->>API: SETTLEMENT_PENDING → SETTLED
```

The client never marks a payment successful. The only path into `PAID_HELD` is a signature-verified webhook **plus** a server-side verify call (spec; job-lifecycle transition #8).

**Net position after 1a–1d:** `gateway_available` +12.50, `platform_revenue` −12.50, `referral_earnings` −2.19, `platform_referral_expense` +2.19. Every other account is zero. The platform keeps 12.50 in cash, recognises 12.50 of revenue, and still owes the referrer 2.19 — net platform revenue **10.31**, exactly the spec's worked example.

## Rules these flows encode

| Rule | Where it shows | Source |
|---|---|---|
| Customer pays exactly the agreed amount | Gateway fee is debited as an expense at capture, not added to the charge | ADR-0003 |
| Provider bears the collection fee | Fee recovered in 1c, 2, 3c, 4b | Spec `gateway_fees` |
| Commission is on the agreed price only | 3c: commission on 20.00, not on the 30.00 item float | Spec, OD-04 |
| Tips are commission-free | 2: no `platform_revenue` line | Spec |
| Promos never reduce provider earnings | 4b: provider gets the same as an unpromoted job, less the smaller actual fee | Spec |
| Referral is 2.5% of net, platform-funded | 1c, 6a | Spec, OD-01 default |
| Referral recalculates on a partial refund | 6a: 2.5% of the reduced net, 131.25 → 1.31 | Spec |
| Clawback can drive balances negative | 7: offset against future earnings; flagged if it stays negative | Spec `referral_program.clawback` |
| Fee on a failed payout is not the provider's loss | 8 | Proposed, platform absorbs |

## Gateway specifics

| Topic | Flutterwave (v3) | Paystack | Stripe (global phase only) |
|---|---|---|---|
| Fee bearer | Set **merchant bears** in every dashboard — default is customer (REPORT §3.1) | Configure `bearer` on the charge/split | Platform account pays fees |
| Actual fee source | Transaction verify response | Transaction verify response | Balance transaction |
| Capture webhook | charge completed event | `charge.success` | `payment_intent.succeeded` |
| Transfer webhook | transfer completed/failed events | `transfer.success` / `transfer.failed` / `transfer.reversed` | `transfer.*`, `payout.*` |
| Settlement | 1–5 business days to merchant balance | Per settlement schedule | Connect balance |
| Hold mechanism | Merchant balance + our ledger; **no dependency on v2 escrow** (ADR-0002) | Same | Separate charges and transfers |

Exact event names and verify-response field names are `VERIFY-IN-RESEARCH` against the sandbox in spike S-12 before they go into contracts; the table records the shape, not final strings.

## Daily reconciliation

1. Pull each gateway's settlement report for the previous day.
2. **Pending ↔ gateway receivable:** sum of `gateway_pending` must equal captured-but-unsettled amounts per the report.
3. **Available ↔ merchant balance:** `gateway_available` must equal the gateway's reported available balance.
4. **Per-transaction match:** every capture, refund and transfer in the report maps to exactly one ledger transaction by `gateway_reference`.
5. Post `1b`-style settlement entries for everything the report confirms.
6. Any difference raises a finance alert and opens a reconciliation case (runbook RB-03). **The ledger is never adjusted to match silently.**

## Invariants for pgTAP

- Every ledger transaction sums to zero and has one currency.
- After a job reaches `CLOSED`, `held_funds` and `item_float` for that job are exactly zero.
- `provider_earnings` credited for a job = agreed amount − commission − gateway fee + float spent + tips − tip fees.
- Sum of refunds for a payment ≤ the payment amount.
- A payout is posted only on a success webhook; a failed transfer posts nothing.
- A referral commission is never posted twice for the same `(request_id, referrer_id)`.
- `platform_revenue − platform_referral_expense − platform_promo_expense` for a period matches the finance report.
