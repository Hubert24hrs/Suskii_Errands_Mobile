# Audit — 2026-09-22 (second pass) — the RLS surface

The first pass that day audited the money. This one audits access: every table, policy, grant and
client-callable function in the schema, against `docs/plan/rls-policy-matrix.md`. The surface has
roughly doubled since it was last read this way (2026-09-17) — 64 tables in `public`, 107
client-callable functions, 14 storage policies, 2 realtime policies.

Four findings. **The first is the pass**: an access control that the matrix specifies on fifty-odd
rows, that has a column in the schema, and that exactly one function honours.

Each item names the migration that fixed it. All four are in
`20260922120700_admin_country_scope.sql` and `20260922120800_provider_card_and_keys.sql`.

## Method

Five mechanical sweeps, then a reading of the matrix row by row.

| Sweep | Looking for | Result |
|---|---|---|
| Tables | a table in `public` without `ENABLE`+`FORCE`, a `REVOKE`, or with a grant wider than the matrix | **clean** — 64 of 64 |
| Policy predicates | `USING (true)`, or `auth.uid()` not wrapped in `(SELECT …)` | three `USING (true)`, all on reference data (`currencies`, `cities`, `zones`); none unwrapped |
| Anon reach | any function or table a signed-out caller can touch | **two functions**, `get_bootstrap` and `get_shared_trip`, both deliberate |
| Function authorisation | a client-callable function that acts on an id it was handed without an ownership or role test | 14 flagged by heuristic, **all 14 false positives** — each checks against a row variable rather than the pattern the sweep grepped for. Listed below so the next pass does not re-flag them |
| Role reach | a role reading rows the matrix scopes | **U.1** |

The 14 false positives, each verified by hand: `accept_offer`, `answer_call`, `cancel_job`,
`counter_offer`, `decline_offer`, `end_call`, `rate_job`, `request_pstn_fallback`,
`set_job_status`, `submit_float_receipt`, `submit_proof`, `unblock_user`, `verify_pin`,
`withdraw_dispute`, `withdraw_offer`.

## U.1 — `R:scope` was decorative (Medium–High, fixed)

**What.** The matrix's legend defines `R:scope` as "read rows within the admin's
country/assignment scope", and fifty-odd cells across the matrix carry it.
`admin_users.country_scope` has existed since Phase 2 to hold that scope. **One function in the
schema reads it** — `kyc_review_queue`. Every other policy was written as
`has_admin_role(ARRAY[...])`: role, not rule.

**Consequence.** A support agent scoped to Nigeria reads Kenya, Ghana, South Africa and Uganda. A
finance officer scoped to one country reads every country's payments, payouts, withdrawals and
payout accounts. A verification officer scoped to one reads every country's provider profiles and
businesses. The column says otherwise and nothing enforces it.

**Why it happened.** Exactly what audit S.1 said the first time: "the policy was written to the
role rather than to the rule, with no note that it was provisional". S.1 caught it on three
tables. This is the same mistake on twenty-eight.

**Severity.** Medium–High. The access is internal, needs an `aal2` admin session, and every read
is attributable — but it is an access control the matrix specifies, the DPIA leans on for a
multi-country platform, and which is worth nothing today. It becomes material the moment a second
country goes live, which `country_pack_readiness` now makes straightforward, so the cost of
leaving it rises rather than falls.

**Fixed.** `private.admin_scope_allows`, and three helpers that take the row's key rather than a
country — `admin_may_read_country`, `admin_may_read_request`, `admin_may_read_user` — so a policy
on a table the caller has no role for costs one function call and no join. Twenty-eight SELECT
policies now scope through them. Two decisions worth stating:

* **`super_admin` is never country-scoped.** The matrix gives it plain `R` in every row, and it is
  the escape hatch for everything else here. `40_admin_scope_test.sql` asserts that a super admin
  *carrying* a country scope still reads both countries.
* **It fails closed.** A row whose country cannot be determined — a profile with no
  `country_code` — is not shown to a scoped officer. An access control that fails open is a
  suggestion, and the alternative is one query away from "show me everything unusual".

**Not covered, deliberately.** `fraud_flags` and `moderation_cases` have polymorphic subjects
(`subject_kind` + `subject_id` as text), so reaching a country means a switch over subject kinds
inside a policy. Both queues are reviewer-facing and small; they are listed here rather than
half-done. `request_media` has no admin branch at all — narrower than the matrix, which says
`R:scope`, and narrower is safe.

## U.2 — a business could rename itself after it was verified (Medium, fixed)

**What.** `organizations` grants `UPDATE (legal_name)` to the owner, with a policy scoped to the
owner and nothing else. The matrix says `U:org-owner(legal_name)` **before verification only**.

**Consequence.** A business verifies as one company and renames itself to another, keeping
`verification_status = 'verified'`. `legal_name` is the only thing about a business a customer
ever sees — the registration number is ciphertext with a blind index and nothing in SQL reads
it — so the verified badge would be attached to a name nobody checked.

**Severity.** Medium. It needs a verified business acting deliberately, and it defeats the point
of verifying businesses at all.

**Fixed.** The `USING` and `WITH CHECK` now require `verification_status <> 'verified'`, which is
the matrix's own wording. The alternative — allow the rename and send the organisation back to
`pending` — is also defensible, and is a policy decision about somebody's ability to trade rather
than a security one; the matrix already states the stricter rule, so that is what is built.

## U.3 — the provider card the matrix names does not exist (Medium, fixed)

**What.** `profiles` is own-read-only and `provider_profiles` is own-read-only, both correct. The
matrix's answer to "then how does a customer choose between three offers" is row 78: `R (public
card fields via get_provider_card() only)`. **That function was never written.**

**Consequence.** A customer comparing offers can learn nothing about the providers — not a name,
not a rating, not whether they are verified. The PRD's offer card ("provider rating, level,
distance, ETA, price") has no source, and the offers board cannot be built against the real
backend. Kimi's M3 board runs on mocks and would have found this at integration.

**Severity.** Medium, and a different shape from the others: it is a hole in the product made by
a correct security decision with its counterpart missing. Recorded here rather than in a backlog
because the reason it is missing is an access-control reason.

**Fixed.** `public.get_provider_card(provider_id)` with the two properties that make it a card
rather than a directory: **a reason is required** — the caller has an offer from that provider, is
on a job with them, or is an admin who may read them, and anything else is
`ERR_PERMISSION_DENIED` rather than an empty row — and **only what a decision needs**: name,
avatar, trust level, verified badge, rating with its count, vehicle type, verified business name,
member since. No phone number, no address, no document, no suspension reason.

## U.4 — the column-grant assertion covered two of five tables (Low, fixed)

**What.** `00_structure_test.sql` asserts "client-writable columns match the RLS matrix exactly"
for `profiles` and `notification_preferences`. Three other tables have column-level write grants —
`requests`, `provider_profiles`, `organizations` — and were unasserted, so a future migration
could widen any of them silently.

**Fixed.** All five are asserted now. `organizations`'s assertion is what keeps U.2's fix honest:
the owner renames it and nothing else, never its verification status.

## Verified, not findings

* **Every table in `public` has RLS enabled and forced**, with an explicit `REVOKE` and grants
  matching the matrix. 64 of 64.
* **`profiles` is own-read-only**, so there is no user enumeration. Everything a client learns
  about another person comes through a `SECURITY DEFINER` function with a reason test.
* **`dispute_evidence` is own-submissions-only for participants**, exactly as the matrix says —
  a customer does not read the provider's evidence.
* **Internal ticket notes do not reach the ticket's owner**: the policy carries `NOT internal`.
* **`kyc-docs` has an INSERT policy and no read policy**, per the spec's "write-only for clients".
* **The three `USING (true)` policies** are `currencies`, `cities` and `zones`. The first two are
  reference data. `zones` holds municipal vehicle rules and ships empty; publishing them to
  clients is the intent, since a rider needs to know where their vehicle is banned.
* **`private.chat_is_open` can be called directly** by any authenticated user with an arbitrary
  request id, which reveals whether that id exists and whether its chat window is open. Reachable
  only by guessing a v4 UUID. Accepted.
