# Audit — 2026-09-21 — Phase 4 and Phase 6 backend, and one gap found while building Phase 8

Findings against my own work. Kimi's findings live in `HANDOFF.md`; each item below names the
commit that fixed it.

## S.1 — Support and dispute roles had blanket read of every conversation, message and call (Medium, fixed)

**What.** The RLS matrix §8 says support reads a conversation "only when a ticket references it,
not by browsing", and calls that a data-minimisation control the DPIA relies on. The policies
shipped in Phase 3 (`conversations_read_participant`, `messages_read_participant`) and the one I
added in Phase 6 (`calls_read_participant`) instead granted every `support_agent` and every
`dispute_officer` read of **every** conversation, message and call on the platform.

**Why it happened.** The table that makes scoping possible — `support_tickets` — is Phase 8 work,
and the Phase 3 policy was written to the role rather than to the rule, with no note that it was
provisional. Nothing failed, because nothing tested it: the matrix was the only place the real
rule was written down.

**Severity.** Medium, not High. The access is internal, needs an `aal2` admin session, and every
read is a staff action against a signed-in account — but it is precisely the over-collection the
DPIA says we do not do, and "we trust our support team" is not a control.

**Fixed** in `feat(support): tickets, the scope they open, and suspension` —
`private.support_ticket_scope(request_id)` is true only when the caller is support or a super
admin **and** a ticket references that job. `dispute_officer` loses the blanket read and does not
get a scoped one, because its scope is the `disputes` table, which does not exist until Phase 5: a
role holding unscoped access while the mechanism that would scope it is unbuilt is the same gap
under another name. `27_support_test.sql` asserts both halves — nothing before a ticket, that job
and only that job after one.

**Closed 2026-09-22** in `feat: referrals, the scopes S.1 left open, and the admin backend`.
`job_events` now reads through `support_ticket_scope` and `dispute_scope`; so do `chat-media`,
`request-media` (through `request_media`, because that bucket's folder is the uploader's rather
than the job's) and `job-proofs`, which gets the dispute scope only — a proof photo carries a
place and a time and is evidence in an argument about money, not context for a support
conversation. Super admin keeps the unscoped read, because the matrix gives it one. Building this
turned up a third gap the finding had not named: the `receipts` bucket the matrix lists did not
exist, so `submit_float_receipt` had been validating a `<request_id>/…` path with nothing behind
it; it is created here with the matrix's own policies. `37_scoped_reads_test.sql` asserts the same
shape throughout — nothing before a ticket or a case, that job and only that job after one.

**Still open.** `location_samples` is not built; it should use the same scope when it is.

## S.2 — A refusal rolled back the record that justified it (Low, fixed)

`request_pstn_fallback` emitted `call.pstn_requested` and then raised, so the event — the whole
reason for building the seam before a telephony vendor exists — never reached the outbox. CI
caught it on the assertion that counted the event. Fixed in `fix(calls): return NULL when there is
no masked number, so the record survives`.

This is the third instance of the same mistake on this project (`verify_pin`'s attempt counter,
the moderation case, this). **The rule: if a function must leave a record behind, it cannot signal
failure by raising.** Return the absence instead, or write the record in a later transaction.

## S.2b — A `CASE` assigned to an enum column, twice (Low, fixed)

`reply_to_ticket` set `status = CASE WHEN … THEN 'waiting_on_user' ELSE 'waiting_on_support' END`.
A `CASE` over string literals resolves to `text`, which will not assign to an enum column, and the
failure is at run time rather than at `CREATE FUNCTION`. The same mistake shipped in the KYC spine
(`81fab85`) earlier the same day.

**The rule: cast the `CASE`, every time.** `(CASE … END)::public.the_enum`. A plpgsql function body
is not type-checked when it is created, so nothing catches this until a test exercises that exact
branch — which is an argument for tests that walk every branch of a state change, not for being
more careful.

Fixed in `fix(support): cast the CASE, which resolves to text`.

## S.3 — Moderation rules are all `[A]` and nobody has read them (Open, tracked)

Every `prohibited_items` row is derived from country packs that tag `restricted: assumption`.
Counsel has not seen the list, and the difference between `block` and `hold` is currently my
judgement about which words are unambiguous. Raised as **OD-24**; the terms are ops-editable data
so a correction is not a release, but the list should not reach a live country unreviewed.

## S.4 — The enforcement that follows a confirmed fraud flag is undefined (Open, tracked)

The risk engine deliberately bans nobody, and `suspend_provider` now exists as the explicit
decision that may follow — bounded, reasoned and audited. What is *not* defined is when it should
be used: which scores, which rules, which repeat patterns. That is the client's policy, not ours.
Raised as **OD-25**.
