# Audit — 2026-09-22 — Phase 5 in full, Phase 6, Phase 8, and the gateway seam

Findings against my own work. Scope: everything written since the audit of 2026-09-21 and not
covered by it — the ledger and its nine parts, the outbox dispatcher and the two Edge Functions,
the referral programme, the admin configuration slice and the analytics views. 6,457 lines of
migration across thirteen files, plus `supabase/functions/payments-*`.

Kimi's findings live in `HANDOFF.md`. Each item below names the migration that fixed it; all five
fixes are in `20260922120400_hardening.sql` unless stated.

**Two of the five would not have been noticed by a test, a reviewer or a user until the day they
cost something.** That is what this pass was for.

## Method

Four mechanical sweeps, then a reading of every money path against `docs/plan/money-flows.md`.

| Sweep | Looking for | Result |
|---|---|---|
| Idempotency | a client-callable function that writes without `idempotency_claim` | 22 hits, 18 naturally idempotent (a toggle, an upsert, a read that logs), 4 noted below |
| Audit S.2 class | a record written and then a raise in the same path | 4 hits, all false positives — every raise precedes its write |
| Audit S.2b class | a `CASE` over string literals assigned to an enum column | 11 hits, all assigning to `timestamptz`, `bigint` or a text-with-CHECK column |
| Grants and RLS | a table in `public` without `ENABLE`+`FORCE`, a policy, or with a grant wider than the matrix | none |
| Ledger keys | a posting reachable twice under two keys | none; every `ledger.post` key is unique per kind and stable across retries |

The reading found four of the five below. The fifth (T.1) came from the grant sweep noticing that
one partitioned table was missing from a list every other one was on.

## T.1 — `webhook_events` partitions were created once and never again (High, fixed)

**What.** `public.webhook_events` is partitioned monthly. The migration created three months of
partitions and scheduled no job to create more. Every other partitioned table in the schema —
`audit.log`, `job_events`, `messages`, `notifications` — has a `pg_cron` entry that keeps them
ahead.

**Consequence.** Roughly three months after a deploy, the first gateway webhook to arrive finds no
partition for its `received_at`. `private.ingest_webhook` raises, the Edge Function answers 500,
the gateway retries and gets 500 again, and **every payment stops being confirmed**. Customers are
charged and their jobs never move. Meanwhile `get_health` stays green: the only partition check in
the schema looks at `audit.log`.

**Why it happened.** The cron line is four lines at the bottom of a migration, written from memory
each time. Four tables had it and the fifth did not, and nothing compares the list to reality.

**Severity.** High. Silent, delayed, and it takes payments down rather than degrading them.

**Fixed.** The missing job, and — because the missing job is only the symptom —
`private.partition_health()`, which looks at *every* partitioned table in `public`, `private` and
`audit`, and a daily `private.record_partition_health()` that writes a `partitions` health check.
`38_hardening_test.sql` asserts that no partitioned table is missing next month's partition, so
the next one somebody forgets fails CI rather than production.

## T.2 — a refund was created and nobody was ever asked to pay it (High, fixed)

**What.** Three functions create a `refunds` row: `cancel_job`, `resolve_dispute` and
`private.release_item_float`. Exactly one of them — `cancel_job` — emitted the
`refund.requested` event that `private.execute_refund` waits for. The other two created the row
and said nothing.

And the one event that *was* emitted went nowhere. `payments-worker` claims the `payment`
aggregate, which is the aggregate `refund.requested` is emitted under, but `dispatch()` had no
branch for it — so it fell through to `default`, was treated as "somebody else's event", and was
**marked complete**. The demand was consumed and discarded.

**Consequence.** A customer owed money by a dispute resolution, or the unspent part of an item
float, never receives it. `refunds_payable` accumulates a liability nothing discharges. The only
signal is a ledger account growing, which nobody is watching yet.

**Why it happened.** The emit was a line in a function rather than a property of the table, so it
had to be remembered three times and was remembered once. The worker's `default` branch was
written for events on aggregates we do not act on, and the refund arrived on one we do.

**Severity.** High. It silently keeps money that belongs to somebody else.

**Fixed.** Three parts:

1. `private.refunds_request_execution()` — an `AFTER INSERT` trigger on `public.refunds`. Creating
   the row is what asks for it, so no future author has to remember. `cancel_job` is replaced to
   drop its manual emit, which is also what stops the gateway being asked twice.
2. The worker gains a `refund.requested` branch, `PaymentProvider` gains `createRefund`, and the
   console provider implements it so the whole path is exercisable today. **Either answer is
   written back** — a refund the gateway refuses is recorded as failed through
   `gateway_fail_refund`, because the platform still owes the money and the books should say so.
3. The worker's `default` branch now logs at `warn` rather than `info`. An unhandled event on an
   aggregate we claim is not routine.

The Flutterwave and Paystack `createRefund` implementations are unwritten for the same reason as
the rest of their adapters: S-12 and merchant accounts.

## T.3 — a chargeback before settlement reversed postings that were never made (Medium, fixed)

**What.** `private.record_chargeback` implements `money-flows.md` posting 7, which is titled
"Chargeback **after payout** (full clawback)" and assumes earnings were recognised. It had no
guard, and a customer can dispute with their bank on day one, while the money is still held.

**Consequence.** On a pre-settlement chargeback the function posted `platform_revenue +12.50` for
revenue never recognised, `provider_earnings +84.60` — **a debt against a provider for money they
never received**, which `private.available_minor` would then net against their next job — and left
`held_funds` at −100.00, so the books said the platform still owed a customer their bank had
already repaid.

**Why it happened.** The posting was implemented from a document that describes one case, and the
other case was not asked about.

**Severity.** Medium rather than High: it needs a chargeback in the first week of a job's life,
and the numbers are wrong rather than the money moving. But it creates a fictitious debt against a
provider, and that is the kind of error somebody discovers by being underpaid.

**Fixed.** `record_chargeback` asks the ledger whether an `earnings_recognised` transaction exists
for the request — the only thing that actually knows — and posts the three-entry reversal when it
does not: the hold released, the gateway's debit, the chargeback fee as a loss. The collection fee
recorded at 1a stays a platform expense, because there was no settlement to recover it from. The
same change refuses a chargeback on a payment that has already been refunded
(`ERR_CHARGEBACK_NEEDS_REVIEW`): the customer has been paid twice and which of the two to unwind
is a person's decision, exactly as an item float already is.

## T.4 — `stacks_with_referral` was configuration that nothing read (Low, fixed)

**What.** `promo_codes.stacks_with_referral` is `NOT NULL DEFAULT false` and is returned by
`preview_promo`. Nothing consumed it. Every promo in the system declared that it does not stack
with a referral, and every promo stacked.

**Consequence.** The platform funds both the discount and the referral on the same job, on every
promo, against its own stated rule. Small per job; the spec lists stacking as a rule to be
configured, so it is a control that was described and not built.

**Severity.** Low — money, but the platform's own, and bounded by promo budgets.

**Fixed.** `private.accrue_referrals` joins `promo_redemptions` to `promo_codes` and pays no
referral on a job redeemed against a non-stacking promo. The anticipated commission rows are
closed out by the same cleanup that handles an expired referral, rather than left to mature.

## T.5 — the analytics export health check called a never-run exporter stale (Low, fixed)

**What.** `analytics.export_health` reports any view whose cursor is older than three days.
Sixteen views were registered with a NULL cursor and no exporter exists to move them, so every
deployed environment would have reported sixteen stale views from the fourth day onwards.

**Severity.** Low, and not a money or data defect — but a health check that cries wolf on day four
is a health check nobody reads on day four hundred, which is when it matters.

**Fixed.** A view that has never run is not stale, it is not started: `export_health` now requires
`last_run_at IS NOT NULL`. A view that ran and then stopped is what the check is for.

## Noted, not fixed

**N.1 — four creates without an idempotency key.** `add_trusted_contact`,
`invite_member`, `accept_organization_invite` and `start_verification_session` write rows without
`private.idempotency_claim`, against CLAUDE.md's "idempotency keys on every create". Three have
natural uniqueness that makes a double-tap a constraint violation rather than a duplicate
(`trusted_contacts` is `UNIQUE (user_id, phone_blind_index)`; `organization_members` is keyed on
the pair). `start_verification_session` has none, so a double-tap creates two sessions. None is in
the money path and all four predate Phase 5. Worth a follow-up; not worth a hurried change to four
functions in a hardening pass.

**N.2 — `ingest_webhook`'s dedupe has a theoretical race across a month boundary.** The explicit
`EXISTS` check catches a retry the partitioned unique index cannot (the index must carry the
partition key). Two concurrent copies of the same event *in the same month* are caught by the
index; two concurrent copies a month apart would not be. Accepted: it needs the same gateway event
delivered twice, a month apart, concurrently.

**N.3 — the outbox accumulates for aggregates nothing drains.** `payments-worker` claims `payment`
and `payout`. Events for `request`, `job`, `referral`, `config`, `dispute` and `admin` stay
undispatched for ever, because the notification and analytics dispatchers do not exist. This is
already handled honestly: `private.health_snapshot()` reports the outbox as `skipped` until ops
sets `ops.outbox_max_age_seconds`, with a comment saying why. Verified, not a finding.

**N.4 — `webhook_events` has RLS forced and no policy at all.** Deliberate, and correct: a raw
gateway payload carries whatever the gateway chose to put in it. Verified.
